What it is

Six stages between a UDP packet and an order

A feed handler is the thing that turns an exchange's raw network traffic into a usable picture of the market. Market data arrives as UDP multicast: framed, segmented, sequenced, and lossy. Nothing about it is a file you can open and parse.

01 receive Strip Ethernet, 802.1Q VLAN, IPv4, UDP. Zero copy. 10.2 ns
02 sequence IEX-TP segments, gap detection, retransmit, A/B feed arbitration. 8.8 ns
03 parse DEEP binary decode. Fixed width, fixed point, no allocation. 26.7 ns
04 book Aggregated-depth order book, sorted structure-of-arrays. The dominant stage. 79.4 ns
05 decide Strategy hook. Deliberately trivial — a placeholder holding a slot in the budget. 5.2 ns
06 encode OUCH-style Enter Order, written straight to the wire buffer. 13.0 ns

Stage costs measured by cumulative prefix on a pinned machine. You can re-measure them on this host in the live instrument below.

Why the transport layer is the hard part

Most order-book projects start after the difficult work is already done

They open a file of already de-framed messages and begin parsing. Framing, segmentation, loss, reordering and duplication have all been solved for them by someone else. That layer is where this project lives.

Every message arrives twice

Exchanges publish market data down two physically separate network paths. You take whichever copy lands first and discard the other. Both feeds carry identical sequence numbers, which collapses the whole problem: A/B arbitration is not an algorithm, it is deduplication by sequence over the merged stream. No A/B-specific branch exists, so the two paths cannot disagree.

A gap is not yet a loss

UDP reorders, so a missing sequence number is buffered rather than declared lost — declaring on first sight would fire constantly on a healthy feed. If the hole persists you request retransmission. If the retransmission never comes you resync, and you record exactly what you lost rather than quietly carrying on with a wrong book.

The wire lies in small ways

Four traps found by running against real captures, not by reading the spec:

802.1QEvery IEX frame is VLAN-tagged. Assuming IPv4 at the usual offset lands four bytes early and misparses the entire file.
.pcapTwo different formats ship under one extension. A classic reader emits plausible garbage from a pcapng file rather than failing.
endianByte order flips mid-packet: Ethernet, IPv4 and UDP are big-endian, IEX-TP and below are little-endian.
65%Of segments in a quiet session are heartbeats. Letting one advance the sequence silently resets the stream.

The flagship measurement error

Coordinated omission: how a benchmark hides its own stalls

Most benchmarks measure service time — how long an item took once work began on it. When the system stalls, the items queued behind the stall are never measured at all, so the stall vanishes from the histogram. Measure instead from each item's scheduled arrival and it reappears.

Offered load, as a fraction of capacity

Corrected latency p50measured from scheduled arrival 125 ns
100 ns10 µs1 ms30 ms
1.4× Below capacity the queue drains between items, so the two agree. A benchmark run only here would look correct.

Service time does not move: 90 ns at every load. It is not lying about the work it timed — it is answering a different question than the one anybody cares about. The system that reports 90 ns at 110% of capacity is, in reality, fifteen milliseconds behind the market.

Measurement discipline

Eight benchmarking bugs. None of them crashed.

Every one produced a plausible number that a reader would have believed. Four of the eight:

−239 nsstage cost
A stage that gave time back. Page faults on the first pass were charged to the warm run before it, and subtracting cumulative prefixes turned the difference negative. The fix is warming, not arithmetic — and the impossible sign is the only reason it was visible.
1.38×threading speedup
A speedup that never happened. Configurations were timed in blocks rather than interleaved, so thermal and scheduler drift over the run landed entirely on one of them. Interleaved, the difference disappears into the noise.
512reported p99
A histogram reporting its own bucket count as the value at the 99th percentile. Dimensionally meaningless, and in the right order of magnitude for a nanosecond figure, which is exactly why it survived review.
0crossed books
The right answer for the wrong reason. The audit inspected the book after market close, when it was empty. An invariant checked against nothing always holds.

This is why every figure the live instrument reports carries its run-to-run spread, and why a difference smaller than that spread is published as unresolved rather than as a result.

Stage budget

Nine timed passes, measured by cumulative prefix: each stage's cost is the difference between running the pipeline up to it and up to the one before. Where that difference is smaller than the run-to-run spread, the row is flagged unresolved — the measurement cannot tell the two apart, so it does not claim to.

Takes a few seconds — nine passes, run one at a time.

Where the design came from

The data chose the data structure

97%
of feed traffic is price-level updates

Measured over a full trading day: 48.80% sell updates, 48.14% buy, 2.94% trade reports, 0.12% everything else. The book's add / update / delete path is the cost of the system, which makes the container choice the whole engineering problem rather than a detail.

2levels
median book depth, over a 480-tick span

This killed the textbook flat-array design. An array indexed by price tick pays for 480 slots to hold a median of two occupied levels — it spends the entire cache line budget on emptiness. Measuring the depth first is what stopped that from being built.

Correctness

What is actually verified

0Crossed books at an event boundary across 38,993,905 updates. IEX splits one logical book event across several messages, so the book is legitimately crossed in between; the check is gated on the feed's event-complete flag, which keeps it strict exactly where it means something.
