The problem, from the start

An exchange broadcasts every change to a list. You have to keep up.

An exchange keeps a list of everyone who wants to buy and sell — at what price, in what size. That list is the order book, and it changes thousands of times a second.

If you want to trade, you need to know what that book looks like right now. So the exchange broadcasts every change as a stream of network packets. Your job is: packets arrive, rebuild the book, decide, send an order. That is the whole loop.

Why it is harder than it sounds

Three things make this difficult, and none of them are about writing fast code.

01

Everyone gets the same packets at the same time

The exchange tells you nothing it is not telling everyone else, simultaneously. The only edge available is who finishes processing first. If a competitor rebuilds the book in 100 billionths of a second and you take 200, they are acting on information you are still reading.

02

The network lies to you

These packets are sent by a protocol that makes no promises. Packets get lost, arrive out of order, or arrive twice. Exchanges send everything twice down separate physical paths precisely because they expect this. You have to notice a gap, take whichever copy lands first, and discard the duplicate — in billionths of a second, never dropping a message.

03

Nothing tells you when you are wrong

There is no correct answer to check against. If your book is wrong, it still looks like a book. You just start trading against a market that does not exist.

What this is

The machine that turns packets into a correct book, quickly.

About 110 nanoseconds from a packet arriving to an order being encoded. Run against 40 million real messages from a real exchange: zero decode errors, zero corrupted books.

The measurement error at the centre of this

How a speed test hides its own stalls

Most speed tests measure how long a task took once it started. If the system stalls, everything stuck waiting behind the stall never gets measured — so the stall vanishes from the results. Measure instead from when each message should have been handled, and it reappears.

Below, the same pipeline at three speeds. The flattering measure never moves. The honest one goes from a rounding error to fifteen milliseconds behind the market.

The flattering number is not lying about the work it timed. It is answering a different question from the one anybody cares about. A system reporting 90 ns at 110% of capacity is, in reality, fifteen milliseconds behind the market.

For engineers — the detail

Six stages between a packet and an order

Costs measured by cumulative prefix on a pinned machine: each stage's cost is the difference between running the pipeline up to it and up to the one before. Where that difference is smaller than the run-to-run spread, no cost is claimed for it.

01 receive Strip Ethernet, 802.1Q VLAN, IPv4 and UDP headers. Zero copy. 10.2 ns
02 sequence Transport segments, gap detection, retransmit requests, A/B feed arbitration. 8.8 ns
03 parse Binary decode. Fixed width, fixed point, no allocation. 26.7 ns
04 book Aggregated-depth order book, sorted structure of arrays. The dominant stage. 79.4 ns
05 decide Strategy hook. Deliberately trivial — a placeholder holding a slot in the budget. 5.2 ns
06 encode Order message written straight into the outbound wire buffer. 13.0 ns

Re-measure the stage budget on this server

Nine timed passes. Where a stage's cost is smaller than the run-to-run spread, the row is flagged unresolved — the measurement cannot tell the two apart, so it does not claim to.

Takes a few seconds — nine passes, run one at a time.

Where the design came from

The data chose the data structure

97%
of feed traffic is price-level updates

Measured over a full trading day: 48.80% sell updates, 48.14% buy, 2.94% trade reports, 0.12% everything else. The book's add / update / delete path is the cost of the system, which makes the container choice the whole engineering problem rather than a detail.

2levels
median book depth, over a 480-tick span

This killed the textbook flat-array design. An array indexed by price tick pays for 480 slots to hold a median of two occupied levels — it spends the entire cache budget on emptiness. Measuring the depth first is what stopped that from being built.

C++20 against Rust: it was the data structure, not the language

The C++ port started 233 ns behind and looked like a language gap. Replacing std::unordered_map with an open-addressed map took it to 146 ns, landing within noise of the Rust build. The difference was never the compiler.

A pricing model that checks itself

Monte Carlo option pricing, validated by requiring its 95% confidence interval to contain the analytic Black–Scholes price — a test that fails when the simulation is subtly wrong, not merely when it crashes.
